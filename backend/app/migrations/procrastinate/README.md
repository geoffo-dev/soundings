# procrastinate schema

Alembic owns the whole database schema, including the job-queue tables of
[procrastinate](https://procrastinate.readthedocs.io/). procrastinate's own
`procrastinate schema --apply` only works on an empty database (it is not
idempotent) and procrastinate keeps no record of which of its migrations ran, so
we follow its guidance for projects with a migration tool: its SQL files are
applied by our Alembic revisions and tracked in `alembic_version`. `soundings
migrate` (= `alembic upgrade head`) is therefore idempotent and upgrade-safe.

The SQL is **vendored** here, never read from the installed package, so an old
revision always runs the same SQL no matter which procrastinate is installed.

| File | Applied by | Contents |
|---|---|---|
| `schema-3.10.0.sql` | revision `0001` (baseline) | full schema of procrastinate 3.10.0, i.e. all of its migrations up to `03.04.00_50_post_add_retry_failed_job_procedure.sql` |

## Upgrading procrastinate

`tests/test_migrations.py::test_procrastinate_upgrade_has_matching_migrations`
fails when the installed procrastinate ships migrations we have not vendored.

1. List the new files: `ls $(uv run python -c "import procrastinate, pathlib; print(pathlib.Path(procrastinate.__file__).parent / 'sql/migrations')")`.
2. Copy every file newer than the last row above into this directory, unchanged.
3. procrastinate splits schema changes into `*_pre_*` files (safe to apply
   before new code is deployed) and `*_post_*` files (apply only once no old
   worker runs). Our migrate Job runs before the rollout, so:
   * add a revision (`make revision m="procrastinate X.Y pre migrations"`, then
     empty the autogenerated body) whose `upgrade()` runs the `pre` files with
     `run_sql_file()` (copy it from the baseline revision);
   * add the `post` files in a revision shipped in the **next** release.
4. Add a row to the table above and bump `PROCRASTINATE_APPLIED_UP_TO` in the test.
